# Zabbix Windows resource exhaustion

> Шаблон Zabbix 7.0: исчерпание ресурсов Windows — сокетов, дескрипторов, пула ядра — с привязкой к процессу.

Шаблон показывает, какой процесс на машине расходует что. Он не привязан к продукту или роли сервера
и использует только стандартные ключи агента: `wmi.getall`, `wmi.get`, `perf_counter_en`, `eventlog`.
Конфигурацию агента менять не нужно.

Этот файл описывает русский шаблон `template/template_windows_resource_exhaustion.yaml`. Английская
версия того же шаблона — `template/template_windows_resource_exhaustion_en.yaml`, её описание —
[README_EN.md](README_EN.md). У файлов общие UUID и имя шаблона, поэтому импорт любого из них обновляет
уже установленный шаблон на месте, с сохранением истории. На сервере стоит одна из двух версий.

**Автор:** Konstantin Tyutyunnik / Константин Тютюнник · [itforprof.com](https://itforprof.com) · MIT

## Зачем

Стандартные шаблоны Windows (`Windows by Zabbix agent` и `... active`) не собирают сокеты, дескрипторы
и выгружаемый пул и ничего не показывают по процессам. Поэтому три частых отказа Windows-сервера
не видны до падения:

- **кончился динамический диапазон портов.** Сервер работает, но приложения не могут подключиться.
  Виновника видно по состоянию сокета Bound, которого нет ни в `netstat` без `-q`, ни
  в `net.tcp.socket.count`;
- **один процесс накопил дескрипторы.** Это видно только в разбивке по процессам;
- **вырос невыгружаемый пул.** Счётчик обычно собирается, но триггера на него в стандартных
  шаблонах нет.

Microsoft в руководстве по исчерпанию TCP-портов советует запустить `netstat -anobq` и найти процесс
с наибольшим числом записей BOUND. Шаблон делает это непрерывно.

## Что собирается

24 элемента на хост и одно правило обнаружения. Раз в пять минут выполняются четыре WMI-запроса:
сокеты, процессы, диапазон портов и объём памяти. Сырые таблицы сокетов и процессов не хранятся,
остальное считается зависимыми элементами за один разбор.

| Раздел | Метрики |
|---|---|
| Сокеты | всего, установленные, CLOSE_WAIT, TIME_WAIT, Bound — из `MSFT_NetTCPConnection` |
| Кто держит | пять процессов с наибольшим числом Bound и CLOSE_WAIT, готовые строки для operational data |
| Динамические порты | свободные порты. Диапазон обнаруживается из `MSFT_NetTCPSetting` |
| Дескрипторы | всего, у самого занятого процесса, пять самых занятых в виде `имя (PID n)=число` |
| Пул ядра | невыгружаемый и выгружаемый, в байтах и в доле физической памяти |
| События Windows | 4231 — эфемерных портов не осталось; 4227 — локальная точка переиспользуется слишком быстро |
| Имена по PID | список `PID=имя` по возрастанию PID, чтобы расшифровать PID из алертов по сокетам |

Графиков три: сокеты по состояниям, дескрипторы и пул ядра, свободные порты в обнаруженном диапазоне.

Диапазон портов шаблон измеряет сам. Правило обнаружения передаёт начало и размер диапазона в элемент
свободных портов и его триггеры, поэтому после `netsh int ipv4 set dynamicport tcp` ничего не нужно
править. Ключ прототипа в Zabbix обязан содержать макрос обнаружения, поэтому смена диапазона создаёт
новый элемент, его история начинается заново, а прогнозу снова нужно шесть часов данных.

## Триггеры

Каждый триггер привязан к пределу ресурса. Детекторов роста здесь нет: на 28 серверах они сообщали
о девяти хостах сразу, а ближайший ресурс был в 35 днях от своего предела. Дескрипторы тогда занимали
2,5% лимита процесса, порты — 1,4% диапазона, невыгружаемый пул — 4,9% RAM.

| Триггер | Важность | Когда срабатывает |
|---|---|---|
| Windows сообщает, что динамический диапазон портов исчерпан | High | событие 4231: свободных портов нет, исходящие соединения не устанавливаются |
| Локальная точка переиспользуется быстрее, чем истекает TIME_WAIT | Warning | событие 4227: одно приложение слишком часто переподключается к одному адресу. Расширение диапазона не помогает |
| Динамический диапазон портов кончается | High | свободных портов меньше `{$WINEX.PORTS.FREE.PCT}`% обнаруженного диапазона |
| Динамический диапазон портов скоро кончится | Warning | прогноз `timeleft` по свободным портам меньше `{$WINEX.PORTS.TIMELEFT}` |
| Соединения не закрываются | Warning | сокетов CLOSE_WAIT больше порога 15 минут, PID виновника в operational data |
| Шторм переподключений | Warning | сокеты TIME_WAIT заняли больше `{$WINEX.SOCK.TIMEWAIT.PCT}`% обнаруженного диапазона |
| Дескрипторов у одного процесса больше порога | Average | суточный минимум дескрипторов самого занятого процесса выше `{$WINEX.HANDLES.CEILING}`. Average: постоянно высокое число — повод для плановой перезагрузки |
| Невыгружаемый пул выше порога | High | выше `{$WINEX.POOL.NONPAGED.PCT}`% физической памяти |
| Выгружаемый пул выше порога | High | выше `{$WINEX.POOL.PAGED.PCT}`% физической памяти |
| Проба сокетов: нет данных | Warning | проба сокетов молчит, а агент жив |
| Проба процессов: нет данных | Warning | проба процессов молчит, а агент жив |
| Пул ядра: нет данных | Warning | счётчики пула молчат, а WMI отвечает |
| Доли пула ядра: нет данных | Warning | доли пула или объём памяти не вычисляются, а агент жив |
| Проба диапазона портов: нет данных | Warning | проба диапазона молчит, а агент жив |

Триггеры «нет данных» срабатывают, только пока агент присылает счётчик пула ядра: он приходит раз
в минуту и не зависит от WMI. Счётчик должен прийти за последние 5 минут и ещё один интервал пробы
назад. Вторая проверка убирает ложные срабатывания после перезагрузки, когда счётчик вернулся,
а проба ещё нет. Если недоступны агент, прокси или канал, счётчик тоже молчит и эти триггеры не
срабатывают. О таком отказе сообщает стандартный шаблон. Прогон по истории за 31 день на 38 хостах
дал два срабатывания, оба — настоящий сбой WMI.

Триггер «Пул ядра: нет данных» не может проверять агента по своему же счётчику, поэтому проверяет его
по WMI-запросу объёма памяти.

У каждой пробы свой триггер «нет данных», и дочерние триггеры зависят только от него: зависший запрос
сокетов не прячет алерты по пулу, данные для которых продолжают приходить. Пока проба молчит, её
дочерние триггеры сохраняют состояние, открытая проблема не закрывается.

У триггеров, которые называют PID, в проблеме есть ссылка «Имена по PID» на расшифровку.

## Требования

- Windows 8 / Server 2012 или новее: раньше нет `root\StandardCimv2` с классом `MSFT_NetTCPConnection`.
- Zabbix agent или agent 2 версии 7.0 или новее, стандартная конфигурация. Проверено на agent 2 7.0.18
  и Windows Server 2025. Агенты старше 7.0 не применяют таймаут элемента к активной проверке.
- Ключ `perf_counter_en`, не `perf_counter`: на локализованной Windows нелокализованный ключ счётчик
  не находит.
- Все элементы — активные проверки. Агенту нужны `ServerActive` на сервер или прокси и `Hostname`,
  совпадающий с именем хоста в Zabbix. Порт 10050 на агенте не нужен.
- Стандартный **`Windows by Zabbix agent active`** привязывается к тому же хосту. О мёртвом агенте
  и неверном `ServerActive` сообщает только он. Сам параметр проверяет
  [zabbix-agent-config-guard](https://github.com/IT-for-Prof/zabbix-agent-config-guard).

## Установка

1. Импортировать `template/template_windows_resource_exhaustion.yaml`
   (`Data collection → Templates → Import`, включить `Create new` и `Update existing`, `Delete missing`
   оставить выключенным).
2. Привязать к Windows-хостам вместе со стандартным шаблоном.
3. Через сутки пройти по хостам, где сработал триггер «Дескрипторов у одного процесса больше порога»,
   и решить, законно ли это. Если законно, переопределить `{$WINEX.HANDLES.CEILING}` на хосте.

Порог дескрипторов — единственный, который может понадобиться переопределять. Порты и пул считаются
долями того, что хост сообщает о себе сам: обнаруженного диапазона и объёма памяти. Для дескрипторов
такого знаменателя в Windows нет. Обычное число зависит от процесса: `dns.exe` держит около 10400 на
любом контроллере домена, здоровый `lsass.exe` — 2000–2500, индексатор `searchd` — 40000–58000.

Триггер дескрипторов читает суточный минимум, поэтому начинает срабатывать через сутки после
привязки. До этого он остаётся в OK.

## Как закрываются проблемы

Триггеры порогов закрываются, когда величина опускается ниже порога. После перезапуска процесса
проблема с дескрипторами закрывается в течение суток: столько нужно, чтобы низкое значение стало
минимумом 24-часового окна. Число в имени события фиксируется при открытии проблемы, текущее
число показано в operational data.

Триггеры журнала событий закрываются через час без новых событий 4231 или 4227. Элемент журнала
получает значения только во время сбоя, и без отдельного условия восстановления проблема не закрылась
бы. Других условий восстановления нет: где оно может выполняться одновременно с условием срабатывания,
Zabbix открывает и закрывает проблему по кругу.

## Макросы

| Макрос | По умолчанию | Смысл |
|---|---|---|
| `{$WINEX.HANDLES.CEILING}` | `100000` | Сколько дескрипторов самый занятый процесс может держать весь день, по суточному минимуму. Самый большой минимум на здоровом хосте парка — 58000 у индексатора поиска |
| `{$WINEX.NODATA.PERIOD}` | `15m` | Сколько проба может молчать до срабатывания триггера «нет данных». Не меньше трёх `{$WINEX.PROBE.INTERVAL}` |
| `{$WINEX.POOL.NONPAGED.PCT}` | `20` | Порог невыгружаемого пула, % физической памяти |
| `{$WINEX.POOL.PAGED.PCT}` | `15` | Порог выгружаемого пула, % физической памяти |
| `{$WINEX.PORTS.FREE.PCT}` | `12` | Минимум свободных портов, % обнаруженного диапазона |
| `{$WINEX.PORTS.TIMELEFT}` | `1d` | На сколько вперёд смотрит прогноз по портам |
| `{$WINEX.PROBE.INTERVAL}` | `5m` | Интервал WMI-проб и глубина проверки живости агента в триггерах «нет данных» |
| `{$WINEX.SOCK.BOUND.FLOOR}` | `500` | Сколько сокетов Bound хост должен держать час, прежде чем прогноз по портам может сработать |
| `{$WINEX.SOCK.CLOSEWAIT.MAX}` | `200` | Сокетов CLOSE_WAIT на хосте в течение 15 минут |
| `{$WINEX.SOCK.TIMEWAIT.PCT}` | `25` | Сокетов TIME_WAIT, % обнаруженного диапазона |
| `{$WINEX.WMI.TIMEOUT}` | `30s` | Таймаут WMI-проб, максимум Zabbix. Перечисление `MSFT_NetTCPConnection` занимает около 4–5 мс на соединение, поэтому проба сокетов перестаёт укладываться в таймаут примерно на 6000–7000 соединений |

Пороги пула заданы долей памяти: на x64 размер невыгружаемого пула ограничен ею. Порог в байтах
оказался бы слишком тесным для большого хоста и слишком свободным для очень большого.

Диапазон портов задаётся командой `netsh int ipv4 set dynamicport tcp start=N num=M`. `MaxUserPort`
в реестре Windows не учитывает со времён Vista.

## Чего шаблон не ловит

- **Утечку до порога.** Процесс, который прибавляет 1000 дескрипторов в сутки от 12000, будет замечен
  через 73 дня, когда пересечёт `{$WINEX.HANDLES.CEILING}`. Если за хостом нужно следить раньше,
  порог понижается на этом хосте.
- **Прогноз по дескрипторам и пулу.** Для `timeleft` нужна история глубже горизонта прогноза. Прогноз
  есть только по портам, где горизонт — сутки.
- **Утечку, размазанную по сотне процессов**, если она не двигает самый занятый процесс. Такая утечка
  поднимет выгружаемый пул, и сработает его порог.
- **Отличие растущей нагрузки от утечки.** Поэтому порог задаётся на хосте человеком, который знает
  роль сервера.
- **Объекты GDI и USER.** У них предел 10000 на процесс, и на терминальных серверах они кончаются
  чаще дескрипторов ядра.
- **Сеансы RDS** — счётчики `\Terminal Services\*`.
