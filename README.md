# Zabbix Windows resource exhaustion

> Универсальный шаблон Zabbix 7.0: исчерпание и утечки ресурсов Windows — сокеты, хендлы, пул ядра — **с атрибуцией по процессам**.

Отвечает на вопрос «кто на этой машине течёт и что кончается». Не привязан ни к какому продукту
и ни к какой роли сервера. Только штатные ключи агента: `wmi.getall`, `wmi.get`,
`perf_counter_en`, `eventlog`. **Правки конфига агента не требуются**, сторонние утилиты не нужны.

## Зачем

Штатные шаблоны Windows (`Windows by Zabbix agent` / `... active`) не собирают **ни одного**
элемента про сокеты, хендлы, пейджируемый пул и вообще ничего в разрезе процессов — там только
`proc.num[]` и `\System\Threads` суммарно. Поэтому три типичных отказа Windows-сервера не видны
до самого падения:

- **исчерпание динамического диапазона портов** — сервер жив, но приложения не могут подключиться.
  Виновника показывает только состояние сокета **Bound**, которого нет ни в `netstat` без `-q`,
  ни в `net.tcp.socket.count`;
- **утечка хендлов в одном процессе** — растёт часами, заметна только в разрезе процессов;
- **рост непейджируемого пула** — счётчик обычно собирается, но триггера на него нет ни в одном
  штатном шаблоне.

Диагностический приём, который шаблон автоматизирует, — канонический: Microsoft в руководстве по
исчерпанию TCP-портов предписывает `netstat -anobq` и поиск процесса с максимумом записей
в состоянии **BOUND**. Здесь это делается непрерывно и заранее, а не постфактум по событиям 4227/4231.

## Что собирается

24 элемента на хост плюс одно правило обнаружения. Два реальных опроса WMI раз в пять минут,
у мастеров `history: 0` — сырой JSON нигде не хранится, всё остальное считается зависимыми
элементами из одного разбора.

| Раздел | Метрики |
|---|---|
| **Сокеты** | всего, established, CLOSE_WAIT, TIME_WAIT, **Bound** — из `MSFT_NetTCPConnection` |
| **Кто держит** | топ-5 процессов по Bound и по CLOSE_WAIT, готовые строки для `opdata` |
| **Динамические порты** | запас свободных портов. Диапазон **обнаруживается** из `MSFT_NetTCPSetting`, а не объявляется макросом |
| **Хендлы** | всего, максимум на процесс, топ-5 в виде `имя (PID)=количество` |
| **Пул ядра** | nonpaged и paged, в байтах и **долей от физической памяти** |
| **События Windows** | 4227 — система сама говорит «порты кончились»; 4231 — переиспользование 4-кортежа, это другое |
| **Справочник** | карта `PID=имя`, отсортированная по PID, для расшифровки сокетных алертов |

Плюс три графика: сокеты по состояниям, хендлы и пул, и график запаса портов на обнаруженный диапазон.

Диапазон динамических портов — единственная величина, которая **измеряется, а не объявляется**.
Правило обнаружения переносит начало и размер диапазона прямо в элемент запаса и его триггеры,
поэтому синхронизировать нечего и разойтись нечему: после `netsh int ipv4 set dynamicport tcp`
всё пересчитывается само. Плата известна — Zabbix требует, чтобы ключ прототипа содержал
LLD-макрос, поэтому смена диапазона заменяет элемент, а не правит его, и история начинается
заново: абсолютный триггер восстанавливается за своё окно, прогнозу снова нужно шесть часов.

## На что реагирует

Логика одна: **алерт обязан называть предел.** Не «растёт ли», а «сколько осталось до того,
чем этот ресурс кончается». Разница не философская: на 28 смешанных Windows-серверах детекторы
роста — они здесь были, четыре штуки — сообщали о девяти хостах одновременно, трое переоткрывались
дважды за два часа, а ближайший ресурс во всём парке отстоял от своего предела на 35 дней. Хендлы
занимали 2.5 % жёсткого лимита, порты 1.4 % диапазона, непейджируемый пул 4.9 % RAM. Рост ресурса
с 97 % запаса — это график, а не тревога, и никакой порог его тревогой не сделает.

Поэтому детекторы роста удалены целиком, а осталось три вида условий:

- **потолок** — доля от физического предела: пул ядра от RAM, запас портов от обнаруженного
  диапазона, хендлы одного процесса против `{$WINEX.HANDLES.CEILING}`;
- **прогноз** — `timeleft` до исчерпания портов, единственное место, где исчерпание реально и быстро;
- **факт** — Windows сама записала в журнал 4227/4231, отказ уже произошёл.

Потолок по хендлам — единственное здесь число, не выводимое из физики: предел на процесс 16 777 216,
и до него не доходит никто, машину раньше ограничивает память ядра. Разброс по парку — от 1722 до
487 426 хендлов у самого занятого процесса, в 283 раза, так что один дефолт верен не везде. Там, где
на хосте законно живёт крупный держатель, `{$WINEX.HANDLES.CEILING}` переопределяется **на хосте**.
Это решение принимается один раз, человеком, днём — и это вся калибровка, которая шаблону нужна.

| Триггер | Уровень | Логика |
|---|---|---|
| Windows confirms the dynamic port range is exhausted | High | событие 4227 — портов в диапазоне не осталось, исходящие подключения падают сейчас |
| Local endpoint reused faster than TIME_WAIT drains | Warning | событие 4231 — переиспользование 4-кортежа. Диапазон при этом почти пуст; чинится в приложении, не расширением диапазона |
| Dynamic port range is running out | High | свободных портов меньше `{$WINEX.PORTS.FREE.PCT}` % обнаруженного диапазона |
| Dynamic port range will run out | Warning | `timeleft` по запасу портов < `{$WINEX.PORTS.TIMELEFT}` |
| Connections are not being closed | Warning | CLOSE_WAIT выше порога, в `opdata` — PID виновника |
| Reconnect storm | Warning | TIME_WAIT занял больше `{$WINEX.SOCK.TIMEWAIT.PCT}` % **обнаруженного** диапазона портов; это не утечка, и триггер так и говорит |
| Handles in one process are above the ceiling | Average | суточный **пол** одного процесса выше `{$WINEX.HANDLES.CEILING}`. Пол, а не последнее значение: процесс, который днём берёт вчетверо больше своего минимума и к ночи отдаёт, за пики не отчитывается. Average, не High: постоянно высокий счётчик — повод запланировать перезапуск, а не повод разбудить |
| Nonpaged pool above the ceiling | High | выше `{$WINEX.POOL.NONPAGED.PCT}` % физической памяти |
| Paged pool above the ceiling | High | выше `{$WINEX.POOL.PAGED.PCT}` % физической памяти |
| Socket probe: no data | Warning | **корень зависимостей**: агент лёг, зонд unsupported или значение обрезано |
| Process probe: no data | Warning | сломался только опрос процессов |
| Kernel pool: no data | Warning | пропал любой из двух счётчиков пула |
| Kernel pool ratio: no data | Warning | доли пула не вычисляются — нет счётчика, чтения памяти или самого расчёта |
| Port range probe: no data | Warning | диапазон портов перестал измеряться |

У каждой цепочки сбора — сокеты, процессы, пул ядра, журнал событий — **свой корень зависимостей**.
Зависимость означает «отказ родителя обессмысливает сигнал ребёнка», а не «они часто падают вместе»:
зависший WMI не должен глушить триггер по пулу, данные которого продолжают идти. Цена — при полном
отказе агента приходит три события вместо одного.

У триггеров, которые называют виновника, в проблеме есть ссылка «PID to name map» и тег
`pidmap_item` — один клик или один вызов API до расшифровки PID.

## Требования

- Windows 8 / Server 2012 и новее — раньше нет `root\StandardCimv2` с классом `MSFT_NetTCPConnection`.
- Zabbix agent или agent 2, дефолтный конфиг. Проверено на agent2 7.0.18 / Windows Server 2025.
- Только `perf_counter_en`, не `perf_counter`: на локализованных Windows нелокализованный ключ счётчик не находит.
- Сервер или прокси должен доставать до агента: всё, кроме журнала событий, — пассивные проверки.
  `eventlog[]` работает только активными; там, где активные проверки не настроены, этот элемент
  молча ничего не соберёт.

## Установка

1. Импортировать `template/template_windows_resource_exhaustion.yaml`
   (`Data collection → Templates → Import`, `Create new` + `Update existing`, `Delete missing` выключен).
2. Прилинковать к Windows-хостам **в дополнение** к штатному шаблону, не вместо.
3. Пройти по хостам, где сработал `Handles in one process are above the ceiling`, и один раз
   решить: это законно крупный держатель или находка. Если законно — переопределить
   `{$WINEX.HANDLES.CEILING}` на хосте. Это единственный порог, который может потребовать
   переопределения: порты и пул считаются долями от того, что хост сам о себе сообщает —
   обнаруженного диапазона портов и измеренной памяти, — а у числа хендлов знаменателя в Windows
   нет ни на одном уровне. Норма принадлежит имени процесса, а не хосту: `dns.exe` держит 10 400 на
   любом контроллере, здоровый `lsass.exe` — 2 000–2 500, `searchd` законно держит 40 000–58 000.
   Формулы, которая накрыла бы всех, не существует — доля от предела в 16 777 216 стоит на четыре
   порядка выше наблюдаемого, а сравнение хоста с самим собой срабатывает на сдвиге в полсотни
   хендлов.
   Полная чувствительность потолка по хендлам — через сутки после линковки, когда заполнится
   24-часовое окно. Раньше этого срока триггер молчит и остаётся в **OK**, а не в Unknown: порядок
   скобок подобран так, чтобы Zabbix обрывал разбор на первом ложном условии. Гарантия начинается с
   первого сохранённого значения; между линковкой и первым значением в Unknown уходит любой триггер
   любого шаблона, и этот не исключение.

## Как закрываются алерты

Штатным способом Zabbix: **когда выражение перестаёт выполняться**. Отдельного
`recovery_expression` нет ни у одного триггера, и это решение, а не упущение.

Отдельное выражение восстановления — второе, независимое условие. Везде, где оно может быть
истинным одновременно с условием срабатывания, Zabbix открывает и закрывает проблему по кругу.
Замерено на реальной истории парка, с той частотой, с какой метрика собирается: у детекторов роста
это давало 57 проблем против 19. Детекторов роста больше нет, но правило осталось в силе для всего,
что сюда добавят.

Триггеры потолка закрываются, когда величина уходит под потолок: пул опускается ниже своей доли
RAM, суточный пол процесса — ниже `{$WINEX.HANDLES.CEILING}`. Процесс, который перезапустили,
отпускает алерт в течение суток — ровно за то время, пока новое, низкое значение вытеснит старое из
24-часового окна. `manual_close` включён там, где закрытие руками осмысленно.

Оба триггера на журнале событий закрываются сами через 30 минут после последней записи: это
подтверждение факта, а не состояние.

## Макросы

| Макрос | Дефолт | Смысл |
|---|---|---|
| `{$WINEX.HANDLES.CEILING}` | `100000` | Сколько хендлов один процесс может держать, прежде чем о нём сообщат независимо от тренда. Читается суточный пол, а не последнее значение, — процесс, который днём выходит на пик и к ночи возвращается, не сообщается за пики. Замерено: самый большой пол на здоровом хосте — поисковый индексатор, 58 000 |
| `{$WINEX.NODATA.PERIOD}` | `15m` | Терпимое молчание зонда. Держать не меньше трёх `{$WINEX.PROBE.INTERVAL}` |
| `{$WINEX.POOL.NONPAGED.PCT}` | `20` | Потолок непейджируемого пула, % от физической памяти |
| `{$WINEX.POOL.PAGED.PCT}` | `15` | Потолок пейджируемого пула, % от физической памяти |
| `{$WINEX.PORTS.FREE.PCT}` | `12` | Минимальный запас портов, в процентах от обнаруженного диапазона |
| `{$WINEX.PORTS.TIMELEFT}` | `1d` | Насколько вперёд смотрит прогноз исчерпания портов |
| `{$WINEX.PROBE.INTERVAL}` | `5m` | Интервал WMI-опросов |
| `{$WINEX.SOCK.BOUND.FLOOR}` | `500` | Сколько Bound-сокетов хост должен держать, чтобы прогноз по портам вообще заговорил. Только прогноз: у детекторов утечек полов нет |
| `{$WINEX.SOCK.CLOSEWAIT.MAX}` | `200` | CLOSE_WAIT по хосту |
| `{$WINEX.SOCK.TIMEWAIT.PCT}` | `25` | TIME_WAIT в процентах от обнаруженного диапазона портов — того, за который они и конкурируют |
| `{$WINEX.WMI.TIMEOUT}` | `30s` | Таймаут WMI-элементов. Потолок Zabbix для агентского элемента; стоимость перечисления соединений растёт вместе с их числом, поднимать выше некуда |

Потолки пула заданы долей от памяти, а не числом байт: на x64 непейджируемый пул ограничен именно
памятью. Фиксированный потолок неверен сразу в обе стороны — тесен для крупной машины, законно
держащей большой пул, и настолько широк для очень крупной, что настоящая утечка до него не дойдёт.

Порога на диапазон портов среди макросов нет намеренно: диапазон измеряется. Задаётся он через
`netsh int ipv4 set dynamicport tcp start=N num=M`, не через реестр — `MaxUserPort` игнорируется
начиная с Vista. Порог задан долей, а не числом, потому что после расширения диапазона любое
фиксированное число значит уже не то.

## Границы

Что этот шаблон сознательно **не** ловит:

- **утечку, пока она не дошла до потолка.** Это главная и осознанная потеря. Процесс, растущий на
  1000 хендлов в сутки от базы в 12 000, не будет сообщён 73 дня — ровно до пересечения
  `{$WINEX.HANDLES.CEILING}`. Детектор роста, который ловил такое, был здесь и удалён: на живом
  парке он сообщал о девяти хостах из 28 одновременно и переоткрывался. Если конкретный хост стоит
  того, чтобы следить за ним раньше, ответ — понизить потолок **на этом хосте**, а не вернуть общее
  правило;
- **прогноза по хендлам и пулу нет.** `timeleft` работает только там, где есть история глубже, чем
  горизонт прогноза; на трёх сутках данных два способа расчёта расходятся в 20 раз. Прогноз есть
  только по портам, где горизонт — сутки. Вернуться к этому, когда наберётся 2–3 недели: в Zabbix
  7.0 для этого есть `trendavg`, `timeleft`, `baselinewma` и `baselinedev`, всё нативно;
- **утечку, размазанную по сотне процессов**, которая не двигает самый занятый. Расчёт на то, что
  такая утечка всё равно поднимет пейджируемый пул, у которого потолок физический;
- **`Reconnect storm` работает только там, где обнаружен динамический диапазон портов** — его порог
  считается от `{#PORT_NUM}`. Если запрос `MSFT_NetTCPSetting` не отвечает, об этом сообщает
  отдельный триггер `Port range probe: no data`, от которого прототипы зависят;
- **растущая штатная нагрузка неотличима от утечки** — и именно поэтому потолок задан на хосте, а не
  выведен из тренда: «много» решает человек, знающий роль сервера;
- **GDI- и USER-объекты не собираются.** У них жёсткий предел 10 000 на процесс — на терминальных
  серверах это более вероятная причина отказа, чем хендлы ядра. Пробел известный;
- **сессии RDS** — счётчики `\Terminal Services\*`.
