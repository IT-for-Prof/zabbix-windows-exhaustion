# Zabbix Windows resource exhaustion

> Универсальный шаблон Zabbix 7.0: исчерпание и утечки ресурсов Windows — сокеты, хендлы, пул ядра — **с атрибуцией по процессам**.

Отвечает на вопрос «кто на этой машине течёт и что кончается». Не привязан ни к какому продукту
и ни к какой роли сервера. Только штатные ключи агента: `wmi.getall`, `wmi.get`,
`perf_counter_en`, `eventlog`. **Правки конфига агента не требуются**, сторонние утилиты не нужны.

## Зачем

Штатные шаблоны Windows (`Windows by Zabbix agent` / `... active`) не собирают **ни одного**
элемента про сокеты, хендлы, пейджируемый пул и вообще ничего в разрезе процессов — там только
`proc.num[]` и `\System\Threads` суммарно. Поэтому три типичных отказа Windows-сервера не видны
до самого падения:

- **исчерпание динамического диапазона портов** — сервер жив, но приложения не могут подключиться.
  Виновника показывает только состояние сокета **Bound**, которого нет ни в `netstat` без `-q`,
  ни в `net.tcp.socket.count`;
- **утечка хендлов в одном процессе** — растёт часами, заметна только в разрезе процессов;
- **рост непейджируемого пула** — счётчик обычно собирается, но триггера на него нет ни в одном
  штатном шаблоне.

Диагностический приём, который шаблон автоматизирует, — канонический: Microsoft в руководстве по
исчерпанию TCP-портов предписывает `netstat -anobq` и поиск процесса с максимумом записей
в состоянии **BOUND**. Здесь это делается непрерывно и заранее, а не постфактум по событиям 4227/4231.

## Что собирается

24 элемента на хост плюс одно правило обнаружения. Два реальных опроса WMI раз в пять минут,
у мастеров `history: 0` — сырой JSON нигде не хранится, всё остальное считается зависимыми
элементами из одного разбора.

| Раздел | Метрики |
|---|---|
| **Сокеты** | всего, established, CLOSE_WAIT, TIME_WAIT, **Bound** — из `MSFT_NetTCPConnection` |
| **Кто держит** | топ-5 процессов по Bound и по CLOSE_WAIT, готовые строки для `opdata` |
| **Динамические порты** | запас свободных портов. Диапазон **обнаруживается** из `MSFT_NetTCPSetting`, а не объявляется макросом |
| **Хендлы** | всего, максимум на процесс, топ-5 в виде `имя (PID)=количество`, **рост пола за 12 ч** — то самое число, которого не хватает в алерте |
| **Пул ядра** | nonpaged и paged, в байтах и **долей от физической памяти** |
| **События Windows** | 4227 / 4231 — прямое сообщение системы «порты кончились» |
| **Справочник** | карта `PID=имя`, отсортированная по PID, для расшифровки сокетных алертов |

Плюс три графика: сокеты по состояниям, хендлы и пул, и график запаса портов на обнаруженный диапазон.

Диапазон динамических портов — единственная величина, которая **измеряется, а не объявляется**.
Правило обнаружения переносит начало и размер диапазона прямо в элемент запаса и его триггеры,
поэтому синхронизировать нечего и разойтись нечему: после `netsh int ipv4 set dynamicport tcp`
всё пересчитывается само. Плата известна — Zabbix требует, чтобы ключ прототипа содержал
LLD-макрос, поэтому смена диапазона заменяет элемент, а не правит его, и история начинается
заново: абсолютный триггер восстанавливается за своё окно, прогнозу снова нужно шесть часов.

## На что реагирует

Логика одна: **утечка — это не большое число, а отсутствие возврата к базовой линии.**
Абсолютных порогов на «сколько хендлов или сокетов держит процесс» здесь нет вообще: на 28 смешанных
Windows-серверах самый занятой процесс держал от 1722 до 487426 хендлов — разброс в 283 раза, при
котором любой дефолт неверен на большей части парка, а per-host переопределения, которые он
вынуждает ставить, хуже отсутствия триггера. Полов у детекторов тоже нет: три условия ниже сами
игнорируют рост с четырёх хендлов до семи, а пол, который на 26 хостах из 28 не пропускает разбор
дальше первого условия, — это порог под другим именем. Пороги остались только там, где потолок физический:
доля пула ядра от RAM и запас портов в динамическом диапазоне.

| Триггер | Уровень | Логика |
|---|---|---|
| Windows confirms TCP port exhaustion | High | событие 4227/4231 — отказ уже произошёл. Подтверждение, не раннее предупреждение |
| Dynamic port range is running out | High | свободных портов меньше `{$WINEX.PORTS.FREE.PCT}` % обнаруженного диапазона |
| Dynamic port range will run out | Warning | `timeleft` по запасу портов < `{$WINEX.PORTS.TIMELEFT}` |
| Bound sockets are not returning to baseline | Warning | пол за 6 ч выше пола за 12 ч, пол за 12 ч выше суточного (оба в `{$WINEX.GROWTH.FACTOR}` раз) **и** окно за 6 ч выше всего предыдущего 6-часового. Второе условие — то, что отличает утечку от рабочего дня |
| Connections are not being closed | Warning | CLOSE_WAIT выше порога, в `opdata` — PID виновника |
| Reconnect storm | Warning | TIME_WAIT занял больше `{$WINEX.SOCK.TIMEWAIT.PCT}` % **обнаруженного** диапазона портов; это не утечка, и триггер так и говорит |
| Handles are not returning to baseline | High | то же правило по хендлам самого занятого процесса. Единственный детектор утечки хендлов |
| Nonpaged pool above the ceiling | High | выше `{$WINEX.POOL.NONPAGED.PCT}` % физической памяти |
| Paged pool is not returning to baseline | Warning | то же правило по байтам пейджируемого пула |
| Nonpaged pool is not returning to baseline | Warning | то же правило по байтам непейджируемого пула |
| Paged pool above the ceiling | High | выше `{$WINEX.POOL.PAGED.PCT}` % физической памяти |
| Socket probe: no data | Average | **корень зависимостей**: агент лёг, зонд unsupported или значение обрезано |
| Process probe: no data | Average | сломался только опрос процессов |
| Kernel pool: no data | Average | пропал любой из двух счётчиков пула |
| Kernel pool ratio: no data | Average | доли пула не вычисляются — нет счётчика, чтения памяти или самого расчёта |
| Port range probe: no data | Average | диапазон портов перестал измеряться |

У каждой цепочки сбора — сокеты, процессы, пул ядра, журнал событий — **свой корень зависимостей**.
Зависимость означает «отказ родителя обессмысливает сигнал ребёнка», а не «они часто падают вместе»:
зависший WMI не должен глушить триггер по пулу, данные которого продолжают идти. Цена — при полном
отказе агента приходит три события вместо одного.

У триггеров, которые называют виновника, в проблеме есть ссылка «PID to name map» и тег
`pidmap_item` — один клик или один вызов API до расшифровки PID.

## Требования

- Windows 8 / Server 2012 и новее — раньше нет `root\StandardCimv2` с классом `MSFT_NetTCPConnection`.
- Zabbix agent или agent 2, дефолтный конфиг. Проверено на agent2 7.0.18 / Windows Server 2025.
- Только `perf_counter_en`, не `perf_counter`: на локализованных Windows нелокализованный ключ счётчик не находит.
- Сервер или прокси должен доставать до агента: всё, кроме журнала событий, — пассивные проверки.
  `eventlog[]` работает только активными; там, где активные проверки не настроены, этот элемент
  молча ничего не соберёт.

## Установка

1. Импортировать `template/template_windows_resource_exhaustion.yaml`
   (`Data collection → Templates → Import`, `Create new` + `Update existing`, `Delete missing` выключен).
2. Прилинковать к Windows-хостам **в дополнение** к штатному шаблону, не вместо.
3. Калибровать ничего не нужно и негде: детекторы утечек сравнивают хост сам с собой.
   Полная чувствительность — через сутки после линковки, когда заполняется самое длинное окно;
   крутой рост ловится раньше. Раньше этого срока триггер молчит и остаётся в **OK**,
   а не в Unknown: порядок скобок подобран так, чтобы Zabbix обрывал разбор на первом ложном условии
   и не доходил ни до окна со сдвигом, ни до вычисляемого элемента, которых ещё нет. Гарантия
   начинается с первого сохранённого значения; между линковкой и первым значением в Unknown уходит
   любой триггер любого шаблона, и этот не исключение.

## Макросы

| Макрос | Дефолт | Смысл |
|---|---|---|
| `{$WINEX.GROWTH.FACTOR}` | `1.05` | Во сколько раз должен подрасти пол — и за 6 ч против 12 ч, и за 12 ч против суток. Единственное число во всех четырёх детекторах |
| `{$WINEX.NODATA.PERIOD}` | `15m` | Терпимое молчание зонда. Держать не меньше трёх `{$WINEX.PROBE.INTERVAL}` |
| `{$WINEX.POOL.NONPAGED.PCT}` | `20` | Потолок непейджируемого пула, % от физической памяти |
| `{$WINEX.POOL.PAGED.PCT}` | `15` | Потолок пейджируемого пула, % от физической памяти |
| `{$WINEX.PORTS.FREE.PCT}` | `12` | Минимальный запас портов, в процентах от обнаруженного диапазона |
| `{$WINEX.PORTS.TIMELEFT}` | `1d` | Насколько вперёд смотрит прогноз исчерпания портов |
| `{$WINEX.PROBE.INTERVAL}` | `5m` | Интервал WMI-опросов |
| `{$WINEX.SOCK.BOUND.FLOOR}` | `500` | Сколько Bound-сокетов хост должен держать, чтобы прогноз по портам вообще заговорил. Только прогноз: у детекторов утечек полов нет |
| `{$WINEX.SOCK.CLOSEWAIT.MAX}` | `200` | CLOSE_WAIT по хосту |
| `{$WINEX.SOCK.TIMEWAIT.PCT}` | `25` | TIME_WAIT в процентах от обнаруженного диапазона портов — того, за который они и конкурируют |
| `{$WINEX.WMI.TIMEOUT}` | `15s` | Таймаут WMI-элементов |

Потолки пула заданы долей от памяти, а не числом байт: на x64 непейджируемый пул ограничен именно
памятью. Фиксированный потолок неверен сразу в обе стороны — тесен для крупной машины, законно
держащей большой пул, и настолько широк для очень крупной, что настоящая утечка до него не дойдёт.

Порога на диапазон портов среди макросов нет намеренно: диапазон измеряется. Задаётся он через
`netsh int ipv4 set dynamicport tcp start=N num=M`, не через реестр — `MaxUserPort` игнорируется
начиная с Vista. Порог задан долей, а не числом, потому что после расширения диапазона любое
фиксированное число значит уже не то.

## Границы

Что этот шаблон сознательно **не** ловит:

- **утечку, размазанную по сотне процессов**, которая не двигает самый занятый. Расчёт на то, что
  такая утечка всё равно поднимет пейджируемый пул, у которого потолок физический;
- **число роста в алерте есть только у хендлов** — `winex.handles.growth`. У сокетов и пула его нет;
- **`Reconnect storm` работает только там, где обнаружен динамический диапазон портов** — его порог
  считается от `{#PORT_NUM}`. Если запрос `MSFT_NetTCPSetting` не отвечает, об этом сообщает
  отдельный триггер `Port range probe: no data`, от которого прототипы зависят;
- **растущая штатная нагрузка неотличима от утечки.** Правило видит пол, который не возвращается;
  сервер, у которого честно прибавляется работы, выглядит так же. Это цена отказа от порогов.

Соседние темы, которые сюда сознательно не попали:

- **аудит перезагрузок** — журнал System (41 / 1074 / 6008 / 6009), наличие и возраст `MEMORY.DMP`,
  признак «ждёт перезагрузки»;
- **сессии RDS** — счётчики `\Terminal Services\*`.
